# Flow Engineering

> **Источник:** Steve Pereira, Andrew Davis. *Flow Engineering: From Value Stream Mapping to Effective Action* (IT Revolution, 2024). Русского перевода нет. Лучший бесплатный конспект: [Dan Lebrero, Book notes](https://danlebrero.com/2024/05/01/flow-enginnering-book-summary/). Официальный обзор: [Пять карт Flow Engineering (IT Revolution)](https://itrevolution.com/articles/the-five-maps-of-flow-engineering/).
> **Повод для внесения:** WP-30/WP-28 (Game Server EvenBet) — нужен системный, последовательный взгляд на поток команды вместо разрозненных методов. Универсальная методология, переносимая за пределы igaming → уровень Pack digital-platform (не доменный igaming-Pack).

## 1. Определение

**Flow Engineering** — серия совместных картирующих упражнений, связывающих непонятное текущее состояние потока создания ценности с ясным путём к целевому состоянию. Отличие от родственных методов — **строгая последовательность из пяти карт**, где выход каждой = вход следующей. Метод стоит на трёх корнях: картирование потока создания ценности (VSM), кибернетика, производственная система Toyota.

**Ключевое отличие от классического VSM:** между «нашли ограничение» и «спроектировали будущее» вставлена **карта зависимостей** — увеличительное стекло на найденное ограничение. Именно этот шаг обычно пропускают, из-за чего будущее состояние получается фантазией.

**Каркас метода:** ценность (цель) → ясность (понимание пути) → поток (оптимизация пути).

## 2. Пять карт (последовательность)

| # | Карта | Таймбокс | Что производит |
|---|-------|----------|----------------|
| 1 | **Карта результата** (Outcome Map) | 60 мин | Общая цель на 6 мес по SMART + выгоды + препятствия |
| 2 | **Карта текущего состояния** (Current State VSM) | 90 мин–2 ч | Как работа течёт сейчас + подсвеченное главное ограничение |
| 3 | **Карта зависимостей** (Dependency Map) | — | Разбор одного ограничения: причины, зависимости |
| 4 | **Карта будущего состояния** (Future State VSM) | 50 мин | Каким поток станет + цели улучшения |
| 5 | **Дорожная карта потока** (Flow Roadmap) | — | Последовательность действий с владельцами и метриками |

### 2.1. Карта результата (60 мин)
Мозговой сброс (5 мин: контекст, цели, боли, идеи, вопросы) → темы → категории → голосование за приоритет → цель по SMART → выгоды (клиент / организация / человек) → препятствия → следующие шаги. Приём: выгоды и препятствия — «тихая рефлексия → пара → группа», не крик с места.

### 2.2. Карта текущего состояния (90 мин–2 ч)
Взять **одну реальную, свежую, типичную** прошедшую через прод задачу → разметить активности **от конца к началу** → к каждой добавить время работы (cycle) и время ожидания (wait) → сквозное время = сумма → подсветить главное ограничение. Правила: «зависит от ситуации» не принимается (дави на типичный случай); при споре бери худший вариант; покрывай 80% потока, крайние случаи игнорь. Мысль: **поток уже существует и течёт — ты его вскрываешь, а не создаёшь.** Цель захода — сразу отыграть 20% времени.

### 2.3. Карта зависимостей
Копия карты потока без всего, кроме ограничения → под-поток внутри этого шага → горячие точки → прямые причины → **5 «почему»** → конфликтующие стимулы и влияние обещаний по срокам. Приём: любопытство, не обвинение; звать тех, кто глубоко знает это место. Цель — найти жизнеспособное улучшение, а не полный анализ.

### 2.4. Карта будущего состояния (50 мин)
Обзор цели (10 мин) → цели улучшения по восьми потерям DOWNTIME (20 мин) → перепроектирование узкого места (10 мин) → оценка новых времён (10 мин). Задача — срезать сквозное время на **80%+ за счёт устранения ОЖИДАНИЯ, а не ускорения работы**. Первый заход: три улучшения за 4-6 недель, не больше. Избыток незавершёнки лечится словом **«нет»**.

Восемь потерь DOWNTIME для умственного труда: дефекты, перепроизводство, ожидание, неиспользованный талант, лишнее перемещение данных, запасы (незавершёнка/очереди), лишние движения (переключение контекста), избыточная обработка.

### 2.5. Дорожная карта потока
Список улучшений → каждое по осям **важность (вертикаль) × выполнимость (горизонталь)** → отметить зависимости → в «сейчас» взять самое важное и выполнимое → метрики прогресса → владелец на каждое действие. Выполнимость падает при: много участников, разрыв компетенций, межкомандные зависимости, неясный объём. Для непонятного — «решения на 15%».

## 3. Формат проведения

- **Группа:** ≤12 человек — ответственные + руководство с полномочиями менять систему.
- **Фасилитатор:** обязательно **вне** этого потока; держит время, не даёт заболтать.
- **Цикл PDSA:** карта будущего = План, дорожная карта = Дело, пересборка карты текущего состояния каждые **3 месяца** = Изучай/Действуй.
- **Философия:** сознательно жертвуют точностью ради скорости и вовлечения. Успех — структурированные разговоры с определённым выходом + психологическая безопасность + итеративность.

## 4. Пять принципов (Lean-корни)

1. **Уточняй ценность** — через обратную связь получателя; доставка кооперативна, не игра с нулевой суммой.
2. **Картируй поток** — видимость → наблюдаемость → ясность.
3. **Создавай поток** — оптимизируй время цикла / сквозное время, а не загрузку людей; нужен запас мощности под колебания.
4. **Тяни, не толкай** — прямая связь потребности и доставки (крайне трудно достижимо).
5. **Гонись за совершенством** — обучение убирает потери, нужна психологическая безопасность.

## 5. Антипаттерны (пять ловушек)

| Ловушка | Симптом | Правильно |
|---------|---------|-----------|
| Пренебречь нарративом | Карта есть, но «зачем» не проговорено → саботаж | Начинать с карты результата |
| Кривые стимулы | Улучшение потока конфликтует с KPI участников | Вскрыть стимулы на карте зависимостей |
| Неполное картирование | Карта обрывается, ограничение вне неё | Мапить от заказа до доставки, включая ожидание |
| Избыточная точность | Недели на «идеальную» карту вместо действия | 80% потока, худший случай при споре, скорость > детали |
| Конфликт с принятой моделью | Метод противоречит уже внедрённому фреймворку | Встроить в существующий язык, не ломать |

Две зашитые фразы: **«обещание по сроку сожрёт всё отпущенное время»**; незавершёнка — **«тихий убийца производительности»**.

## 6. Когда применять / связь с семьёй методов

- **Вход в незнакомую команду/конвейер** — до Аналитика ограничений (DP.ROLE.054): Flow Engineering даёт последовательность «куда смотреть», прежде чем TOC Five Steps выбирают, что чинить.
- **Карта зависимостей (шаг 3)** — прямой предшественник **Stage Dependency Map (DP.WP.016)**: обе про зависимости вокруг ограничения. Flow Engineering вскрывает причины, DP.WP.016 фиксирует план устранения как граф этапов.
- **Отличие от bottleneck-pick/TOC:** bottleneck-pick отвечает «что чинить первым» на готовой структуре работ; Flow Engineering сначала строит эту структуру через совместные карты. Sequencing: Flow Engineering (собрать поток и найти ограничение) → Аналитик ограничений (выбрать TOC-инструмент) → Декомпозитор (разбить на артефакты).
- **Измерение** дополняется четырьмя метриками Kanban Guide (незавершёнка, пропускная способность, возраст элемента, время цикла) и опросником «пять воров времени» (DeGrandis).

## 7. Применение в наших РП

- **WP-30** (управление потоком задач Game Server) — карты 1-3 закрывают «диагноз боли до интервенции»: карта результата = встреча с CTO (зачем и критерии годности), карта текущего состояния = уже собранная разбивка входов, карта зависимостей = правила входа как ограничение.
- **WP-28** (карта погружения GS/Go) — карта текущего состояния как формат наблюдения потока через границы функциональных команд.
- **DP.ROLE.054 / bottleneck-pick** — Flow Engineering как pre-step перед TOC-каскадом при `--layer=intra`.

## 8. Revision criterion

- Would change if эмпирика покажет, что разовые картирующие сессии не удерживают эффект без постоянной канбан-системы (тогда — субординировать STATIK/канбану, а не наоборот).
- Would change if появится русский перевод или более строгая формализация последовательности пяти карт.
