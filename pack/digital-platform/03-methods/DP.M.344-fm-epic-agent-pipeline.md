# DP.M.344 — FM Epic Agent Pipeline

## Описание

5-этапный конвейер для управления эпиком с помощью агента: агент несёт состояние и черновики, пилот тратит время только на решения и отправку.

## Алгоритм

**Этап 1 — Утренний снимок:**
Агент по расписанию получает из трекера: текущее состояние задач эпика, дельту за сутки (новые, закрытые, изменившие статус), застои (задачи без движения > N дней), черновики корзин — конкретные предложения для разблокировки.

**Этап 2 — Файл состояния + реестр решений:**
Агент пишет state-файл и обновляет реестр решений. Цель: ответить на вопрос «статус?» за минуту без обхода трекера вручную.

**Этап 3 — Проверка тона:**
Перед показом пилоту исходящие сообщения проверяются агентом на тон (эскалационность, неоднозначность). Пилот видит уже откорректированный черновик.

**Этап 4 — write-task с проверкой готовности:**
Запись задачи в трекер — только после явного «да» пилота на конкретный текст. До записи: проверка чеклиста готовности задачи (все обязательные поля заполнены).

**Этап 5 — Замер потока + сверка реестра:**
Еженедельно: замер потока по дням недели (выявление узких дней); полная сверка реестра решений с текстами задач трекера (см. DP.M.340 Decisions Drift Check).

**Этап 6 (следующая волна):** смоук-чеклисты из требований, сгенерированные при старте игры/фичи.

## Ключевые инварианты

- Агент читает трекер только на чтение (GET); мутации — только после явного «да» пилота на конкретный черновик.
- Конвейер параметризован эпиком: те же скрипты переключаются на следующий эпик без переписывания.
- Разделение: чтение (всегда безопасно) vs запись (требует подтверждения + ограниченный контекст).

## Применимость

Любой Feature Manager, ведущий эпик с параллельными задачами и несколькими исполнителями. Конвейер снижает стоимость ежедневного контроля: «обход трекера руками» → «прочитать файл состояния, ответить на черновики».
