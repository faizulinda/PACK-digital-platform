# DP.M.339 — Варианты до продуктовых решений, код после подтверждения

## Обещание

Агент сохраняет автономию в технических решениях и предоставляет пилоту управление продуктовыми развилками — без необходимости явно описывать границу в каждом PR.

## Определение проблемы

При разработке продукта ИИ-агентом (Claude Code, Cursor и т.п.) размыта граница: что агент решает сам, а что требует одобрения. Без явного классификатора агент либо слишком часто спрашивает (тормозит работу), либо вносит незапрошенные продуктовые изменения.

## Классификатор

| Тип решения | Определение | Действие агента |
|-------------|-------------|-----------------|
| **Продуктовое** | Меняет *что* видит пользователь или *в каком порядке* — состав экрана, поведение фичи, приоритет задач | Предложить 2–3 варианта с рекомендацией, подождать подтверждения |
| **Техническое** | Видно только в diff — имена переменных, структура кода, тесты, рефакторинг | Агент решает сам, сообщает post-factum |

## IPO-паттерн

| Элемент | Описание |
|---------|----------|
| Входы | Задача, затрагивающая продуктовую развилку (UX, состав, поведение) |
| Обработка | Классификатор: «меняет ли это продукт для пользователя?» → Да → варианты; Нет → реализация |
| Выходы | Для продуктовых: 2–3 варианта с рекомендацией до первой строки кода. Для технических: код + краткое пояснение |

## Шаги метода

1. Перед реализацией любого нетривиального изменения — применить классификатор.
2. Если **продуктовое**: сформулировать 2–3 варианта (включая «оставить как есть»), указать рекомендованный и причину.
3. Дождаться явного выбора пилота.
4. Если **техническое**: реализовать, описать решение в PR/коммите.

## Граница применения

- Применяется: фичи, изменения UX, переработка flow, изменение порядка элементов.
- Не применяется: баг-фиксы с очевидным единственным решением, внутренний рефакторинг без видимого эффекта.
