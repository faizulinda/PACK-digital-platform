# DP.M.340 — Конфиг фиксируется на атомарную операцию, а не на сессию

## Обещание

Параметры операции не меняются в её середине; изменение конфига в real-time не прерывает текущую операцию и вступает в силу предсказуемо.

## Определение проблемы

В системах с долгоживущими сессиями (игровые раунды, финансовые транзакции, долгие API-запросы) конфиг может измениться в середине операции. Это приводит к: изменению условий для пользователя без его ведома; несогласованным вычислениям внутри одной операции; сложной логике компенсации.

## IPO-паттерн

| Элемент | Описание |
|---------|----------|
| Входы | Начало атомарной операции (ставка принята, транзакция открыта, джоб запущен) |
| Обработка | Snapshot актуальных параметров конфига → привязать к операции ID |
| Выходы | Операция завершается с теми же параметрами, с которыми началась; следующая операция берёт обновлённые значения |

## Алгоритм

1. В момент старта атомарной операции — считать параметры конфига и зафиксировать snapshot.
2. Все вычисления внутри операции используют snapshot, не live-значения.
3. Изменение конфига в admin/API — немедленно принимается системой, применяется к следующей операции.
4. Если параметр виден пользователю (House Edge, комиссия, ставка) — до применения нового значения уведомить пользователя и получить подтверждение.

## Когда применять

- Игровые раунды (ставка → результат)
- Финансовые транзакции (курс берётся при создании)
- Batch-джобы (параметры джоба фиксируются при старте)
- API-запросы с промежуточными шагами (multi-step checkout)

## Антипаттерн

Читать конфиг в каждом шаге операции — изменение параметра между шагами меняет условия посреди операции без уведомления.

## Силы

| Полюс | Полюс | Напряжение |
|-------|-------|------------|
| Операция видит свежий конфиг (актуальность) | Операция видит стабильный конфиг (согласованность) | Snapshot разрешает напряжение в пользу согласованности |
