# DP.M.334 Формулировка задачи на уровне интерфейса

## 1. Определение

Метод формулировки задачи для мостов и интеграций: задача описывается как «что именно пересекает границу и в какой момент», а не «как реализовать». Изоляция компонентов задаётся через структуру директорий или данных, а не через правила доступа.

## 2. Проблема

Когда bridge/интеграция формулируется как «как это сделать», стоимость неизвестна и растёт при реализации. Если зафиксировать интерфейс (что передаётся, в какой момент агент видит факты) до начала кода, реализация становится детерминированной.

## 3. IPO-паттерн

| Элемент | Описание |
|---------|----------|
| Вход | Задача мост/интеграция с неизвестной стоимостью |
| Обработка | Явно назвать: что пересекает границу, в какой момент, через какую структуру (не правила) |
| Выход | Задача с фиксированным интерфейсом → реализация за 1–2 дня |

## 4. Шаги метода

1. Для каждого компонента моста явно назвать: **что** передаётся через границу.
2. Явно назвать: **в какой момент** агент/компонент видит переданные факты.
3. Зафиксировать изоляцию через **структуру** (директории, схема данных), а не через правила доступа.
4. Только после фиксации интерфейса — переходить к реализации.

## 5. Применимость

Любая задача мост/интеграция между компонентами, системами, личными и рабочими контекстами. Применимо к агентным системам, межсервисным интеграциям, разделению контекстов.

## 6. Forces

| Полюс | Полюс | Напряжение |
|-------|-------|------------|
| Начать с кода и разобраться по ходу | Сначала назвать, что пересекает границу | Код даёт ощущение движения, описание границы кажется задержкой |
| Изоляция правилами доступа | Изоляция структурой | Правила гибче, структура надёжнее и не требует соблюдения |

## 7. Bias-Annotation

| Смещение | Направление искажения |
|----------|------------------------|
| Недооценка цены неясной границы | «Задача понятна» принимается за «интерфейс известен» → реализация стартует до фиксации границы, стоимость растёт по ходу |
