# DP.FM.187 — Batch-update падает на одной записи с полем длиннее ограничения столбца — остальные записи не обновляются

## Описание

При пакетном обновлении через интеграцию (API → БД) одна запись с полем, превышающим ограничение столбца (VARCHAR 255), роняет весь батч — остальные записи не обновляются. Интеграция не сигнализирует о частичном провале, данные по другим записям молча устаревают.

## Пример

Интеграция внешнего провайдера: пакетное обновление каталога падает на одной записи с заголовком длиннее 255 символов («Data too long for column …»). Одна запись роняет всё обновление. Историческая причина: старые записи созданы до введения валидации длины на стороне источника.

## Тест обнаружения

«Валидируется ли каждая запись батча по схеме (длина строк, типы) перед отправкой?» Нет → риск полного провала батча от одной невалидной записи.

## Инвариант

Отсутствие per-record pre-batch валидации создаёт зависимость: одна невалидная запись = полный провал батча. Следствие: данные по остальным записям устаревают без явного сигнала.

## Митигация

1. Pre-batch валидация: проверять каждую запись отдельно на соответствие схеме столбцов (длина, тип, nullable)
2. Graceful skip или карантин «плохой» записи с логированием — не остановка всего батча
3. Алерт при пропуске записи с указанием причины нарушения
